# Secure OTA Provisioning Backend

A security-first backend foundation for wearable secure-element provisioning. This repository starts as a modular monolith with explicit boundaries for the provisioning orchestrator, device registry, Crypto/HSM adapter, Interswitch adapter, and audit trail. It can be split into independently deployed services later without changing the domain contracts.

## Current slice

- Go 1.22 HTTP API using the standard library
- Explicit provisioning state machine
- Idempotent session creation with Supabase PostgreSQL persistence when `DATABASE_URL` is configured, plus an in-memory fallback for local development
- Supabase Auth bearer-token verification using the project's asymmetric JWKS keys; session ownership is taken from the verified token subject
- Slice 3 attestation orchestration with one-time challenges, request binding, replay protection, and counter checks
- Durable device-key revocation checks, typed failure codes, redacted audit events, and an HSM-only verification port
- Owned device registry with hashed device identifiers, opaque device IDs, provider/key registration, key rotation, revocation, replacement, suspension, resumption, and retirement
- AWS KMS asymmetric verification adapter; KMS keeps the verification key under AWS HSM protection and is enabled only with an exact configured key ID
- Google Play Integrity decode adapter with OAuth service-account authentication, package/request-hash binding, app-recognition, licensing, certificate-digest, and device-integrity policy checks
- Development-only mock Crypto/HSM and token adapters; production token requests use the configured Interswitch OAuth adapter, while device crypto and APDU hardware remain explicit fail-closed ports
- Health and readiness endpoints
- Redis-backed distributed rate limiting and attestation abuse controls
- PostgreSQL schema for the production persistence boundary
- Remaining-stage orchestration behind explicit authentication, Interswitch, payload-wrapper, APDU-channel, and device-verification interfaces
- Docker Compose for PostgreSQL and Redis dependencies
- Prometheus-compatible metrics at `/metrics`, OpenTelemetry OTLP HTTP tracing, and structured security-event export

## Test strategy

Run fast unit tests with `go test ./...`. The PostgreSQL integration suite uses a real PostgreSQL server, applies the repository migrations in a private ephemeral schema, and verifies migration replay, checksum verification and drift rejection, legacy checksum baselining, forward upgrades, transactional failure recovery, concurrent canonical-fingerprint idempotency and optimistic-lock races, device registration/replacement/lifecycle races, attestation-key binding and rotation, webhook deduplication, and database constraint failure behavior. It never substitutes an in-memory repository for the database path. For local execution, point `DATABASE_URL` at a disposable database and run `make test-integration`; the suite removes only its generated schema. CI runs the same suite against PostgreSQL 16. Do not point this command at staging or production.

Provider acceptance is intentionally separate from database integration: Apple App Attest tests require genuine provider-signed artifacts, and the staging KMS script performs live signing and verification with the configured AWS KMS key. Do not generate synthetic provider tokens or use fabricated responses as evidence of provider interoperability. The repository's existing `scripts/staging-kms-e2e.ps1` is the opt-in live AWS KMS/API acceptance path and requires staging credentials and an authenticated user token.

## Run locally

```bash
go run ./cmd/api
```

The API listens on `:8080` by default.

### Local containers

Copy `.env.example` to `.env`, then run `make local-deps` to start PostgreSQL and Redis with health checks and loopback-only published ports. To start the containerized API, run `make local-app`; it waits for both dependencies and enables the embedded, transactionally applied migrations with `AUTO_MIGRATE=true`. Automatic migrations are rejected unless `ENVIRONMENT` is `development` or `local`, and are disabled by default outside this explicit Compose profile. `make local-down` stops the services; named database volumes remain unless explicitly removed with `docker compose down -v`.

The API still requires a reachable Supabase Auth issuer with a valid asymmetric JWKS document. The default issuer in `.env.example` is the configured Supabase project; override `SUPABASE_AUTH_ISSUER` for a local Supabase Auth service whose signing configuration publishes ES256 or RS256 public keys. Do not turn off token verification to make local startup succeed. No synthetic user rows, provider assertions, seeded credentials, or token generator are included; use a real account and provider-backed artifacts for authenticated acceptance checks.

Redis is not an unused dependency: it backs distributed rate limiting and abuse-control state. Development can fall back to bounded in-process limiting if Redis is not configured, while staging and production require Redis. The Compose profile starts Redis and configures the API to use it.

Set `DATABASE_URL` to the Supabase connection string to use durable PostgreSQL sessions and audit events. If it is omitted, the service uses the development-only in-memory repository. Set `REDIS_URL` to the Redis connection string for distributed rate limiting; staging and production require both durable PostgreSQL and Redis.

When `ENVIRONMENT=staging` or `ENVIRONMENT=production`, `DATABASE_URL` is mandatory and startup fails closed rather than using memory persistence. Apply all migrations from `migrations/001_init.sql` through `migrations/018_bounded_retention_purge_indexes.sql` using the approved deployment migration process before starting production; automatic migration startup is deliberately prohibited outside development. The runner stores a SHA-256 checksum beside every applied migration and fails closed on missing checksums, unknown ledger versions, or checksum drift. Migration files already deployed must be treated as immutable; add a new numbered migration for changes. For an existing database whose ledger predates checksums, first compare the deployed schema and historical release artifacts to this exact reviewed source revision, take a verified backup, then run `DATABASE_URL=<protected-connection-string> go run ./cmd/migration-baseline --accept-current-migration-files-as-baseline` once during a controlled maintenance window. Migration 012 was the first ledger; the explicitly approved baseline therefore also records versions 001–011 when version 012 exists, avoiding replay of historical DDL that predates the ledger. This operator-confirmed command fills only missing hashes, preserves and checks any existing hashes, applies pending migrations transactionally, and refuses unknown versions or drift. Never use the baseline flag to legitimize a changed historic migration; if the historical files cannot be verified, stop and reconcile the database with a documented migration/restore plan instead. Migration 006 initializes a global provider/key counter from the greatest value already stored in `device_attestations`. Migration 007 enables RLS and revokes direct grants for `anon` and `authenticated` on the application tables. Migration 008 persists the public key extracted from a validated Apple App Attest object for subsequent assertion verification. Migration 009 stores the device registry and opaque session-to-device binding; raw device identifiers are hashed in PostgreSQL. Migration 010 stores the server-built canonical request document alongside each challenge. Migration 011 adds the monotonic session version used for optimistic state-transition locking. Migration 012 creates the schema migration ledger and records the validated deployment version. Migration 013 adds server-only provisioning stage metadata. Migration 014 persists webhook event IDs and SHA-256 fingerprints of the verified session/token-reference payload under a unique constraint. Migration 015 adds a server-only token-request operation ledger with a stable per-session idempotency key and explicit pending, unknown, and succeeded outcomes. Migration 016 records the successfully validated 001–015 baseline in the ledger; it prevents the pre-ledger migrations from being replayed at every subsequent startup. Migration 017 binds each new session idempotency key to a 32-byte SHA-256 fingerprint of a versioned canonical creation request; legacy sessions without a fingerprint reject replay under that old key rather than silently accepting unverified request changes. Migration 018 adds composite indexes used by bounded retention cleanup.

Provisioning state changes use compare-and-swap semantics. Each session has a positive `version`; a transition updates the row only when the version read by the request is still current, then increments it atomically. Concurrent stale writers receive a conflict instead of overwriting a newer state. The in-memory adapter applies the same contract for development and tests, so behavior does not change between environments.

Session creation first atomically reserves the idempotency key with its canonical request fingerprint, before calling the device registry. A matching retry for a fully linked session returns it without registry work. Reuse of that key for a different user, device UID, model, or transport returns `409 Conflict` before registry work. The request fingerprint is versioned, hashed, stored server-side, and never returned in the API. During an interrupted or concurrently executing first creation, a matching request can safely resume registry linking; PostgreSQL registry uniqueness makes that recovery idempotent and ensures only one device row. Existing pre-migration sessions have no recoverable request fingerprint (the raw device UID is intentionally not stored), so retries using those old keys fail closed and clients should use a new key for new requests.

Token issuance uses a durable claim before any provider call. The winning transaction moves the session to `TOKEN_REQUESTING` and creates one operation row; concurrent requests and subsequent retries do not call the provider again. A provider timeout, process crash, or unpersisted response leaves the operation `PENDING` or `UNKNOWN` for reconciliation instead of blind retry. A verified provider webhook can resolve that operation atomically. Inspect unresolved operations with a read-only query such as `SELECT o.session_id, o.idempotency_key, o.status, o.last_error_code, o.updated_at, s.state FROM token_request_operations o JOIN provisioning_sessions s ON s.id = o.session_id WHERE o.status IN ('PENDING', 'UNKNOWN') OR s.state = 'TOKEN_REQUESTING' ORDER BY o.updated_at;`. This includes a provider success recorded after session expiry; that operation is not an authorized provisioning transition and may require provider-side revocation. Reconcile against the provider using the stored key where supported; do not manually retry an uncertain request. `INTERSWITCH_SUPPORTS_IDEMPOTENCY_KEY` defaults to `false` and adds the `Idempotency-Key` header only after the exact provider product contract confirms that behavior. For rollout, stop or drain all older API instances before enabling this version; a mixed-version deployment can still execute the old provider-before-persistence flow. Existing pre-upgrade sessions in `SESSION_AUTHENTICATED` should be reconciled or allowed to expire before token requests resume.

The API applies an atomic Redis Lua token bucket to the transport peer IP before authentication. Session creation adds a per-user policy. Challenge generation and attestation verification add both per-user and per-device policies. Failed cryptographic or request-binding attestation attempts place short-lived Redis penalty keys on the user and device, while expired, replayed, unavailable-provider, and persistence-related errors are not treated as attacker-controlled signature failures. Rate-limit keys contain SHA-256 identifiers rather than raw user, device, or IP values. Redis is required and must pass a live ping before staging or production startup; local development can use the bounded in-memory implementation when `REDIS_URL` is absent.

`/healthz` is a process-liveness check. `/readyz` is a bounded dependency check and returns `503` until required checks pass. In staging and production it verifies the PostgreSQL connection, every expected migration ledger entry and its SHA-256 checksum against the embedded migration files, cached or freshly fetched Supabase JWKS keys, active attestation-provider configuration and readiness, and that the real InterSwitch client/webhook verifier are wired rather than the development mock. The InterSwitch check is configuration-only: it does not call the provider or establish product-contract acceptance. Missing, unknown, or drifted migration records fail readiness without modifying the database. AWS KMS readiness performs a non-mutating `DescribeKey` check and requires an enabled key. Google Play readiness validates the configured service-account credentials and package configuration without sending a fabricated integrity token. Apple App Attest readiness validates the configured trust anchor, identifiers, environment, and durable key lookup. The JSON response reports only check names and statuses and does not expose credentials or provider endpoint details.

`.github/workflows/test.yml` runs on pull requests, pushes to `main`, and version-tag pushes. It validates workflow syntax with pinned `actionlint`, checks module checksums and graph consistency, runs `govulncheck` against the Go code and standard library, executes unit/race and real PostgreSQL integration tests, builds the container, and blocks the image gate on HIGH or CRITICAL OS/library findings. GitHub Actions are pinned to full commit SHAs; Dependabot checks weekly for Go module, action, and Docker base-image updates. The Go toolchain is pinned to Go 1.27.4, and the builder, distroless runtime, and PostgreSQL integration image use digest references.

The container job builds locally under a tag derived from the source commit; it does not log in to a registry, push an image, or deploy. It generates an SPDX JSON SBOM for that exact built image and records the source commit, image config digest, archive SHA-256, SBOM SHA-256, and toolchain in `release-metadata.json`. The image archive, SBOM, metadata, and scan report are uploaded as a uniquely named, non-overwritable GitHub Actions artifact with 30-day retention. This is a CI artifact, not a production release; registry publication, signing, and deployment are intentionally not configured.

To make the gates mandatory, configure repository rulesets outside this code: protect `main` against force-push/deletion and require pull requests plus the `Go tests, dependency validation, and vulnerability scan`, `PostgreSQL 16 migration and persistence integration`, and `Container build, vulnerability scan, SBOM, and immutable artifact` checks. Add a tag ruleset for `v*` that restricts creation to release maintainers and blocks tag updates/deletion. Rulesets and required-check settings are GitHub repository controls and are not changed by this repository patch. Treat a failing vulnerability gate as a remediation item; do not broadly ignore findings or make scans informational without documented, expiring exceptions and security-owner approval.

## Data retention and bounded purge

The repository includes a standalone, manually invoked purge command; it does not create or enable a recurring schedule. This implementation deliberately defines no retention periods. Before running it, the data owner must approve and supply all four retention windows based on applicable law, card-scheme/provider contracts, dispute and chargeback needs, security investigations, and operational recovery requirements. The required environment values are `RETENTION_EXPIRED_CHALLENGE_AGE`, `RETENTION_EXPIRED_SESSION_AGE`, `RETENTION_WEBHOOK_EVENT_AGE`, and `RETENTION_AUDIT_EVENT_AGE`, each a positive Go duration; `RETENTION_PURGE_BATCH_SIZE` is independently required and must be between 1 and 1000. Missing, zero, negative, or malformed policy values fail closed. Do not copy durations from examples or select them without the authorized policy owner.

After migration 018 is applied and verified, inject `DATABASE_URL` and the approved values through the deployment secret/configuration mechanism, then run `make retention-purge` once. Each invocation commits one PostgreSQL transaction, acquires a non-blocking advisory lock, and deletes no more than the configured batch size from each eligible category using indexed age cutoffs and `FOR UPDATE SKIP LOCKED`. Repeated executions must be explicitly initiated by the operator or an externally governed scheduler; this repository does not configure one. Results report deleted row counts only.

The cleanup considers expired challenges by `expires_at`, webhook metadata by `received_at`, audit records by `created_at`, and sessions by `expires_at`. Migration 018 also adds a server-only `provisioning_retention_holds` ledger. An active `GLOBAL` hold makes the command fail closed without deleting data; an active `SESSION` hold preserves that session and its linked audit, challenge, webhook, attestation, and token-operation rows. Holds must be created and released through a privileged, controlled operator procedure that records `created_by`/`released_by` and a bounded reason code; the API does not expose hold management. A session is eligible only after its own session age and all linked challenge, webhook, session-attestation, and resolved token-operation age conditions are satisfied; each child table is independently batch-limited, so a session remains until a later invocation if any child rows remain. It is also held back while any audit row remains, while a token operation is `PENDING` or `UNKNOWN`, or while the session is `TOKEN_REQUESTING`. Those held records require reconciliation or a later approved purge. Session-specific `device_attestations` are removed in their own bounded batch after the linked session exceeds the session-retention cutoff, but global `device_attestation_counters`, registered devices, and device-key lifecycle/revocation state are intentionally never deleted because they protect replay detection and ownership/key lifecycle. Audit data can be deleted only under the separately approved audit-retention window. Validate approved windows, backup/restore posture, active holds, and behavior in a non-production environment before any production invocation; this mechanism is not a compliance certification.

## Observability

`GET /metrics` exposes an application-owned Prometheus registry. HTTP request metrics use normalized route labels rather than raw paths, and dependency metrics cover readiness operations for PostgreSQL, Redis, Supabase JWKS, and the configured attestation provider. Attestation failure metrics use stable provider and failure-code labels so dashboards can group cryptographic, replay, binding, and provider-availability failures without recording assertions or tokens.

When `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` is configured, the service exports server spans over OTLP/HTTP with `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES_ENVIRONMENT` resource attributes. Shutdown flushes the batch span processor. Leave the endpoint empty when trace export is intentionally disabled.

Audit events continue to be written to durable PostgreSQL in production and are also emitted as allowlisted structured JSON log records. The export excludes assertions, access tokens, raw device UIDs, and request bodies. `SECURITY_ALERT_WEBHOOK_URL` can be set to deliver failure events to an HTTPS alert receiver; payloads contain only opaque IDs and stable event codes, and are signed with `SECURITY_ALERT_WEBHOOK_SECRET` using `X-Alert-Signature: sha256=<hex>`.

## Remaining provisioning stages

After device attestation, the service exposes owner-scoped actions for session authentication, token request, token receipt, payload wrapping, APDU transfer, device verification, completion, and explicit failure. Actions validate the expected predecessor state and persist through compare-and-swap or purpose-built atomic repository transactions. Provider outcomes are recorded without leaking credentials or raw provider errors. Token-request errors are treated as potentially ambiguous: the operation remains `TOKEN_REQUESTING` for reconciliation and is never blindly retried.

The protocol-neutral HTTP contract is published in [`api/openapi.yaml`](api/openapi.yaml). Every session action below is `POST /v1/provisioning-sessions/{session_id}/<action>`, requires a verified `Authorization: Bearer <access-token>`, and returns 404 for both missing and non-owned sessions. Routes are: `authenticate` (`{"proof":"..."}`), `token-request` (empty body), `wrap-payload` (empty body), `transfer-apdu` (empty body), `verify-device` (`{"proof":"..."}`), `complete` (empty body), and `fail` (`{"failure_code":"UPPERCASE_CODE"}`). Proof values are opaque, non-empty JSON strings capped at 65,536 Unicode code points (subject also to the overall request-body cap); no format or card-level meaning is assumed. JSON rejects unknown fields and additional top-level values. Failure codes are 1–64 uppercase ASCII letters, digits, or underscores; free-form error details are not accepted. The token is received only by the existing signed provider callback `POST /v1/webhooks/interswitch`, not by a caller-controlled session action.

Stage errors have stable machine-readable `failure_code` values and do not return underlying provider, cryptographic, or APDU errors. The contract maps invalid input to 400, missing/non-owned session to 404, state/concurrency conflicts and unresolved token operations to 409, expiry to 410, generic stage rejection to 422, an unconfigured real stage adapter to 501, and unavailable required dependencies to 503. Payload wrapping, APDU transport, session-auth proof semantics, and device-verification rules remain dependent on the approved Verve/card integration profile. The routes do not accept caller-supplied payload bytes or APDU sequences; missing adapters fail closed. These HTTP contract tests establish routing, validation, ownership, and error behavior only; they are not card/provider acceptance tests and do not simulate successful card operations.

The session expiry boundary is inclusive: a new token request is rejected before contacting the provider at or after `expires_at`. A webhook that would newly advance an expired `TOKEN_REQUESTED` or `TOKEN_REQUESTING` session is rejected under the repository's atomic state lock and does not reserve an event ID or payload fingerprint. Retries of a callback already accepted before expiry remain idempotent after expiry.

The Interswitch adapter currently uses an OAuth 2.0 client-credentials flow over TLS, parses expected JSON response fields, uses bounded HTTP clients, and does not fabricate token values. Configure the exact product-specific sandbox URLs and credentials supplied by Interswitch with `INTERSWITCH_TOKEN_URL`, `INTERSWITCH_REQUEST_URL`, `INTERSWITCH_CLIENT_ID`, and `INTERSWITCH_CLIENT_SECRET`. Token webhooks require a configured secret, event ID, timestamp within a bounded replay window, and a constant-time HMAC comparison before the state transition is attempted. Migration 014 atomically commits the event ID and token-received transition, rejects reuse of an ID with different content, and stores only a SHA-256 fingerprint of the session/token-reference pair for retry idempotency. The event ID header is not included in the current HMAC input; correctness therefore relies on the signed body plus session state and payload deduplication, not on the header as an authenticated claim. The exact Interswitch webhook signature profile must match the API product contract; the adapter does not guess undocumented fields. Validate this implementation against the vendor's actual signature profile before production activation.

**InterSwitch provider acceptance is not complete.** The implemented OAuth request/response fields, token-request JSON, idempotency behavior, webhook header semantics, and HMAC canonicalization remain unverified against the selected InterSwitch product. Existing adapter tests use a local in-process transport only. See the [InterSwitch acceptance gate and live test matrix](docs/interswitch-acceptance.md) for the authoritative contract inputs, sandbox checks, evidence handling, and release no-go criteria. Do not enable the idempotency-key option or claim token/webhook acceptance until the product contract is confirmed and the live sandbox matrix is completed.

Payload wrapping is an injected cryptographic boundary. The provided AES-GCM wrapper binds ciphertext to the session and correlation ID and uses a fresh random nonce; production deployments should source its key from the approved HSM/KMS ceremony rather than application source or logs. APDU transfer is similarly injected through a secure-channel transport. A production hardware adapter must implement the GlobalPlatform SCP03 mutual-authentication, command-integrity, response-integrity, and confidentiality contract; without that adapter the stage fails closed instead of simulating a card.

Migration 013 adds server-side token reference, wrapped payload, and APDU receipt fields. These fields are never serialized in the public session response. Google Play Integrity attestation is returned and stored with `binding_scope: session`; its verdict is not accepted as proof of a persistent device-held key, and it does not register or revoke caller-provided key IDs. Use a separate platform credential/attestation mechanism when persistent device-key binding is required.

The API verifies Supabase Auth access tokens against `SUPABASE_AUTH_ISSUER` and `SUPABASE_AUTH_AUDIENCE` (defaults for this project are shown in `.env.example`). It loads the project's public JWKS at startup, refreshes keys on rotation and every five minutes, and accepts only ES256 or RS256 tokens with the expected issuer, audience, expiration, a non-empty subject, and the `authenticated` role. This follows Supabase's [JWT verification guidance](https://supabase.com/docs/guides/auth/jwts) and [signing-key guidance](https://supabase.com/docs/guides/auth/signing-keys). All `/v1` routes require `Authorization: Bearer <access-token>`; health and readiness routes remain public. The `user_id` request field is no longer accepted: the verified `sub` claim becomes the session owner. A valid Supabase user login is required to obtain an access token for API use.

The selected user sign-in is Supabase email OTP or magic link. Supabase's client method is `signInWithOtp`; it sends a magic link by default, or a code when the Email Magic Link template contains `{{ .Token }}`. The client verifies a code using `verifyOtp({ email, token, type: 'email' })`, then sends the resulting access token to this API as a bearer token. See Supabase's [passwordless email guide](https://supabase.com/docs/guides/auth/auth-email-passwordless). This repository contains the backend only; the production web/mobile sign-in screen must call Supabase Auth directly with a publishable key, never the service-role key.

For a real user-to-API acceptance check, start the API and set `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and (if needed) `OTA_API_BASE_URL` in the environment, then run `powershell -ExecutionPolicy Bypass -File scripts/auth-email-otp-e2e.ps1`. The script requests a real email OTP, securely prompts for the code, verifies it with Supabase, creates a provisioning session using the returned user access token, and reads that session back as its owner. It does not print or persist the OTP or access token. It sends an email, creates the Supabase Auth user if the address is new, and creates a provisioning session; use an address you control and treat this as a mutating live test.

Email authentication is enabled by default in Supabase, but its built-in SMTP is intended for development: delivery is restricted to project team addresses and has a low rate limit. Before production, configure a reputable custom SMTP provider, a verified sender/domain with SPF/DKIM/DMARC, the project's Site URL and exact allowed redirect URLs, email confirmation, a short OTP expiry, and the Magic Link template appropriate to code or link sign-in. Keep SMTP credentials in Supabase's protected Auth configuration, not this repository. See Supabase's [custom SMTP production guidance](https://supabase.com/docs/guides/auth/auth-smtp). These project-level settings and a real-user test remain unverified; the code and test harness alone do not certify email delivery.

Set `AWS_KMS_KEY_ID` to enable the AWS KMS verifier. The API then accepts `provider=aws-kms` only when the submitted `key_id` exactly matches that configured key. The assertion is a base64url-encoded JSON envelope containing `signature` (base64url) and a positive `counter`; the signature covers the canonical challenge message, and the counter is persisted atomically per provider/key across provisioning sessions. The runtime loads AWS credentials through the standard AWS SDK credential chain and never receives a private key.

To enable the Google Play Integrity adapter, set `ATTESTATION_PROVIDER=google-play-integrity`, `GOOGLE_PLAY_INTEGRITY_PACKAGE_NAME` to the exact Android package name, and either `GOOGLE_PLAY_INTEGRITY_CREDENTIALS_FILE` to a secret-mounted service-account JSON file or `GOOGLE_PLAY_INTEGRITY_CREDENTIALS_JSON` from a protected secret store. The submitted assertion is a base64url-encoded JSON envelope containing the opaque `integrity_token`; omit `key_id` because Play Integrity does not attest a stable device-held key. The backend sends the token to Google’s decode endpoint and validates the package name, server-issued request digest, `PLAY_RECOGNIZED` app verdict, licensing when required, configured certificate digest, allowed device-integrity verdict, and a bounded timestamp freshness window (five minutes by default). The response is explicitly session-scoped. Service-account keys must not be committed or printed.

To enable the Apple App Attest adapter, set `ATTESTATION_PROVIDER=apple-app-attest`, `APPLE_TEAM_ID`, `APPLE_BUNDLE_ID`, `APPLE_APP_ATTEST_ENVIRONMENT`, and `APPLE_APP_ATTEST_ROOT_CERT_FILE` to a secret-mounted copy of Apple’s official App Attestation Root CA certificate. Initial registration accepts a base64url JSON envelope containing `attestation_object`; subsequent verification accepts `assertion` and the exact client-data bytes. The verifier validates the Apple certificate chain, App ID hash, environment, credential ID, COSE P-256 key, nonce, validation category, bundle version, assertion signature, monotonic counter, challenge, and server-computed request digest. The attestation challenge endpoint has an empty request body and returns the server-built request document plus `request_digest`; clients must include that digest in Apple client data as `request_digest`. The API rejects client-supplied `request_hash` fields and does not accept caller-supplied public keys.

This repository change does not enable APIs, create service accounts, alter IAM, link Play Console, or access Google Cloud resources. Those operations remain an external deployment step. Until the Google project is linked to the Android application and valid production token fixtures are supplied, the provider must remain fail-closed in staging and production.

For a non-mutating Windows check of the external prerequisites, run `powershell -ExecutionPolicy Bypass -File scripts/google-play-integrity-preflight.ps1 -ProjectId <project-id> -PackageName <package-name> -CredentialsFile <secret-file>`. The script only reads project metadata and service-account inventory; it never enables APIs, creates accounts, changes IAM, displays key material, or changes Play Console.

This adapter is valid only for a protocol where the signing key corresponding to the configured KMS asymmetric key is the authorized verification key. AWS KMS `Verify` cannot validate arbitrary device public keys just because their IDs are submitted. It is therefore not a replacement for Apple App Attest, Android Play Integrity, or a per-device public-key registry; those providers still require their own certified verification paths.

AWS KMS must use an asymmetric `SIGN_VERIFY` key whose signing algorithm matches `AWS_KMS_SIGNING_ALGORITHM`. CloudHSM is not silently substituted: a direct CloudHSM deployment requires the separately approved PKCS#11 adapter, cluster networking, crypto-user secret handling, key registry, and HSM operational controls. Until that adapter is configured, the service remains fail-closed.

Before any mutating staging walkthrough, the read-only preflight can check the exact authorized HTTPS origin, `/healthz`, `/readyz`, and an authenticated `GET /v1/devices`: set `SUPABASE_ACCESS_TOKEN` in the current PowerShell process, then run `powershell -ExecutionPolicy Bypass -File scripts/staging-readonly-preflight.ps1 -ApiBaseUrl 'https://<staging-host>' -ExpectedApiOrigin 'https://<staging-host>'`. It discards the device list and makes no session/device/provider/card changes. Readiness confirms the InterSwitch adapter is configured in staging/production, but does not contact or validate the provider.

The existing `scripts/staging-kms-e2e.ps1` walkthrough uses the configured AWS KMS key and the running API. It creates sessions with synthetic device metadata, signs a backend-defined message using the server KMS key, and checks KMS/API integration plus selected attestation state/replay behavior. This is **not** genuine wearable-held attestation, provider token acceptance, APDU transport, or card acceptance. It creates persistent staging sessions; run only with an authorized test account and cleanup/retention plan. It uses `AWS_PROFILE` when set, otherwise the AWS default credential chain; there is no hard-coded developer profile. See the [live staging acceptance runbook](docs/staging-acceptance.md) for required genuine-device/provider/card evidence and stop/go criteria.

## Device registry

The authenticated device endpoints are `GET /v1/devices`, `POST /v1/devices`, `POST /v1/devices/{device_id}/suspend`, `POST /v1/devices/{device_id}/resume`, `POST /v1/devices/{device_id}/revoke`, `POST /v1/devices/{device_id}/retire`, and `POST /v1/devices/{device_id}/replace`. Registration and replacement accept `device_uid`, `device_model`, and `transport`; revocation and lifecycle changes require a non-empty reason. Responses expose only the server-generated opaque device ID and metadata, never the raw identifier or public key.

Creating a provisioning session ensures that the authenticated user owns the device identifier and stores the opaque device ID on the session. Attestation is rejected unless the device is usable and the submitted provider/key is either newly registered for that device or already bound to it. A successfully verified new key atomically replaces the previous active key for that provider. Revocation, suspension, replacement, and retirement are enforced before cryptographic verification and are also persisted in the key lifecycle records. This follows NIST SP 800-63B authenticator binding/lifecycle guidance, NIST SP 800-57 key registration and revocation guidance, and OWASP API1:2023 object-level authorization guidance.

## Security boundary

The mobile app must never receive manufacturer master keys, HSM credentials, raw PAN, or long-lived provider credentials. The mock adapters intentionally return deterministic development values and must be replaced with certified integrations only after the device protocol, Interswitch contract, key ceremony, HSM policy, and compliance scope are approved.

Supabase application tables are server-only: RLS is enabled without client-facing policies, and direct grants are revoked from `anon` and `authenticated`. The API must connect through a trusted privileged database role. Do not expose `DATABASE_URL` to clients. Direct Supabase REST access to these tables is intentionally denied; if a future client data path is required, add verified identity-to-owner mappings and narrowly scoped RLS policies before exposing it.

Every `/v1` call must carry a valid Supabase Auth user access token. The API validates its signature using only asymmetric project public keys, pins issuer and audience, requires the `authenticated` role, and uses the signed subject for authorization. Never accept a caller-supplied `user_id` as identity. The project currently advertises ES256 public keys at the issuer's JWKS endpoint; the verifier also supports RS256 key rotation and rejects shared-secret algorithms.

## PostgreSQL backup and restore rehearsal

The repository provides `scripts/postgres-backup-rehearsal.sh` and `make backup-rehearsal` for a **local-only PostgreSQL 16 logical backup rehearsal**. It creates a compressed custom-format `pg_dump` archive, lists the archive TOC, records a SHA-256 manifest in a newly created private output directory, restores into an internally generated disposable database using `pg_restore --single-transaction --exit-on-error`, runs `ANALYZE`, checks the restored migration ledger/checksum lengths, and drops the disposable restore database on exit. It never drops or overwrites the source database and refuses a restore database name supplied by the operator. A non-zero exit means the rehearsal did not complete successfully; failed output is retained for investigation.

Configure a libpq service file with a **local Unix socket only** and use the appropriate trusted local authentication. The script accepts no passwords or connection strings on its command line, requires `PGSERVICEFILE`, rejects PG connection environment overrides and remote host settings, checks PostgreSQL 16 client and server versions, and sets backup artifact permissions to owner-only. For example, create a private `PGSERVICEFILE` outside the repository with:

```ini
[local-rehearsal]
host=/var/run/postgresql
```

Then run against a disposable PostgreSQL 16 source database (not staging or production):

```bash
PGSERVICEFILE="$HOME/.pg_service.conf" make backup-rehearsal PGSERVICE=local-rehearsal SOURCE_DB=provisioning_test
```

Set `OUTPUT_DIR=/secure/path/new-directory` to select a new output directory. The directory must not already exist. Backup files contain sensitive operational data: protect them with restrictive filesystem permissions, approved encryption at rest, access control, off-host storage, and retention/deletion controls before using them outside a local rehearsal. Do not upload or commit archives, manifests, or TOC files. Local `backups/` outputs are git-ignored.

This is not a production backup service or a compliance certification. A `pg_dump` archive is a consistent **single-database logical backup**; it does not contain cluster-wide roles or tablespaces, and is not a physical base backup, continuous WAL archive, or point-in-time recovery (PITR) solution. `pg_dump` archives do not establish that external KMS keys, provider credentials, object storage, application secrets, Redis state, or identity-provider configuration are recoverable. Production restore procedures must decide role/ownership handling and verify all required extensions/privileges in the actual hosting environment; this rehearsal preserves source ownership/ACL metadata and therefore requires compatible roles/permissions when restoring.

Before production reliance, select and document an approved backup owner, schedule, encryption/key management, immutable/off-site storage, retention and deletion policy, monitoring/alerting, access controls, backup integrity checks, and restore authority. The service owner must approve recovery point and recovery time objectives (RPO/RTO). If PITR is required, configure and test provider-supported base backups plus continuous WAL archiving; a logical dump alone cannot meet that requirement. Rehearse restoration into an isolated, access-controlled target, verify application readiness and migration checksums, and record elapsed restore/validation times. Production backup storage/provider configuration, live environment restore, PITR, and RPO/RTO are intentionally not claimed or configured here. Guidance: [PostgreSQL 16 backup and restore](https://www.postgresql.org/docs/16/backup-dump.html), [continuous archiving and PITR](https://www.postgresql.org/docs/16/continuous-archiving.html), and [NIST SP 800-34 Rev. 1 contingency planning](https://csrc.nist.gov/pubs/sp/800/34/r1/upd1/final).
